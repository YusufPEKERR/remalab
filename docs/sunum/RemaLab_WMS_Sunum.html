04 Veri Akışının Kalbi

Frontend ↔ Backend köprüsü

Frontend'deki her api.xxx() çağrısı, Python'daki bir @Slot metoduna denk gelir. Python her zaman bir JSON string döndürür; frontend JSON.parse eder. services/api.js bu köprünün tamamını Promise'lere saran tek katmandır.

  • Her uç nokta bir callback alır, {"success": true, …} döner.
  • Büyük yük varsa {fetch_url:"/api_cache/…"} döner → frontend ikinci bir fetch() yapar.
  • Köprü 3 sn'de kurulamazsa devreye mock backend girer.
// frontend/src/services/api.js
login: async (u, p) => {
  const backend = await getBackend();
  return new Promise((resolve) => {
    backend.login(u, p, (res) =>
      resolve(JSON.parse(res)));
    // └─ Python @Slot WebBridge.login
  });
}
React → api.js → QWebChannel → @Slot (Python) → SQLAlchemy → JSON → React
05 Performans Deseni

api_cache — veriler nereden geliyor?

Parçalar, stok, ürünler on binlerce satır olabilir. Bu kadar veriyi köprüden JSON string olarak geçirmek yavaştır. Çözüm: veriyi diske serileştirip HTTP ile okumak — ve her commit'te otomatik tazelemek.

DB'den çek, diske yaz

get_parts, get_stock_status, get_products veriyi çeker ve api_cache/*.json dosyasına yazar.

Köprüden kısa cevap dön

Koca JSON yerine yalnızca {"success": true, "fetch_url": "/api_cache/parts.json"} döner.

Frontend dosyayı HTTP ile indirir

Arayüz /api_cache/parts.json adresini doğrudan çeker — köprü tıkanmaz.

Commit'te otomatik geçersizleştir

SQLAlchemy after_commit dinleyicisi her veritabanı commit'inde parts · stock · critical önbeleğini siler → sonraki okuma güncel veriyi yeniden üretir.

Kavram düzeltmesi api_cache/ dışarıdan gelen bir API verisi değildir — kendi PostgreSQL'inizin hız için diske alınmış anlık görüntüsüdür. (İsim benzerliğine rağmen uzak api/ REST servisinden bağımsızdır.)

07 Tanılama Entegrasyonu

Phonecheck ile test akışı

Cihaz testleri bir bulut tanılama servisi olan Phonecheck ile entegredir. IMEI ile cihaz sorgulanır, sonuç bir statü geçişine dönüştürülür ve kanıt olarak saklanır.

  • Sonuç eşlemesi: yanıt → Pass1 (geçti) · Fail1 (Failed/Working=No) · None (Pending — test bitmemiş, geçiş yapılmaz).
  • Manuel yedek: cihaz Phonecheck'te yoksa (404) operatör veriyi elle girer — zorunlu gerekçe (manual_reason) ile.
  • Deneme limiti: her (IMEI, test aşaması) için en fazla 10 başarısız deneme.
  • Kanıt: sonuç phonecheck_test_result'a (grade, batarya döngüsü/sağlığı, ham parça JSON) yazılır; hatalar test_result_fault'a düşer.

08 Onarım Motoru

Eşzamanlı onarım & demontaj kararı

Cihaz 109 (Üretim Aşaması)'na ulaştığında, tespit edilen arızalara göre departman başına paralel onarım kayıtları (RepairRecord) üretilir. Her biri bağımsız bir alt iş emridir.

Filtrele & Koru algoritması

  • Arızalı her kategori için ItemCategoryMission görevleri havuzlanır; cihazın zorluk kademesi ProductFamilyMission'dan bulunur.
  • KURAL 1: genel montaj görevleri (L1/L2) yalnızca cihaz o kademeyi destekliyorsa tutulur.
  • Uzmanlık koruma: L3REPAIR · BATTERY · DISPLAY · CAMERA · CASE görevleri her zaman korunur.
  • Önceliklendirme: BATTERY (0) → L3 (1) → diğerleri (2).

13 Uçtan Uca Örnek

"İrsaliye ile parça girişi"

Tek bir kullanıcı aksiyonunun katmanlar arasında nasıl aktığını izleyelim — arayüzden veritabanına ve geri bildirime kadar.

Kullanıcı formu doldurur

İrsaliye sayfasında parça + lokasyon + adet + birim fiyat girip kaydeder.

Köprü çağrısı

Frontend api.addInboundEntry(...) → services/api.js bunu backend.add_inbound_entry(...)'a köprüler.

Tek transaction (Python)

add_inbound_entry: stock bakiyesini artırır (yoksa oluşturur) + stock_movements'a "Inbound" satırı yazar (created_by, unit_price, total_cost) → commit().

Önbellek geçersizleşir

Commit → after_commit dinleyicisi stock · parts · critical önbelleğini siler.

Geri bildirim

Frontend {"success": true} alır; Depo / Rapor ekranları güncel veriyi görür. Kritik limitin altına düşen parça, periyodik yoklamayla bildirim zilinde belirir.

14 Kimlik & Güvenlik

Roller ve güvenlik durumu

Giriş login ile yapılır — kullanıcı bulunur, bcrypt ile parola doğrulanır, profil döner ve frontend depolamasına (local/session) yazılır. Menü, operasyon rollerine göre gruplanmıştır.

login
Kullanıcı + bcrypt doğrulama → profil (id, username, tc_no, rol, görev, müdür zinciri). JWT altyapısı mevcut ama masaüstü akışı güvenilir yerel köprüye dayanır.
roller
Yedek parça personeli · test personeli · demontaj / üretim teknisyeni · onarım havuzu · ara test · admin. DEVELOPER rolü Admin sayılır.
son admin
delete_user son kalan Admin'i silmeyi reddeder.
Dürüst güvenlik notu Menü rol filtresi kodda şu an kapalıdır (tüm kullanıcılar tüm menüleri görebilir) ve backend @Slot metodlarında endpoint bazlı rol kontrolü yoktur — köprüye bağlı herkes çağırabilir. Ayrıca .env'de düz metin DB parolası bulunur, bazı DB-gezgini uçları tablo adını doğrudan SQL'e gömer. Bunlar üretim sertleştirmesi için bilinen ve değerlendirilmesi gereken risklerdir.
